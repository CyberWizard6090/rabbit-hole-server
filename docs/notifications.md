# Уведомления

Полный список маршрутов и схем: [`openapi.yaml`](openapi.yaml). Realtime-канал: [`realtime.md`](realtime.md).
Почта: [`mail.md`](mail.md).

## Как событие становится уведомлением

```
изменение в БД  ->  запись активности (после коммита)  ->  диспетчер  ->  каналы
```

1. Сервис пишет запись активности через `ActivityRecorder` в `txhook.AfterCommit`, то есть только после
   успешного коммита.
2. `NotifyingRecorder` передаёт запись `NotificationDispatcher` (очередь в памяти, 1024 пакета).
3. Диспетчер сопоставляет тип активности с планом (`notification_events.go`): кому, какого типа, что автоматически
   добавить в наблюдатели. Автора события он исключает, кроме технического владельца задачи из формы.
4. Для каждого получателя проверяются права на задачу или форму и настройки типа и канала.
5. Уведомление записывается в приложении, остальные каналы получают доставку.

Сбой доставки не влияет на запрос, который породил событие.

## Типы

| Ключ | Когда | По умолчанию |
|---|---|---|
| `mention` | упоминание в комментарии (`mention_user_ids`) | приложение, e-mail, webhook |
| `assigned` | назначение на задачу или пункт чек-листа | приложение, e-mail, webhook |
| `comment` | новый комментарий в наблюдаемой задаче | приложение |
| `status_changed` | смена статуса | приложение |
| `due_date_changed` | смена срока | приложение |
| `form_submission` | новая отправка формы (получатели в `settings.notify_on_submit`) | приложение |

Настройки по типам и каналам: `GET/PUT /notifications/preferences`.

## Наблюдатели

`PUT/DELETE /tasks/{id}/watch`, `GET /tasks/{id}/watchers`. Создатель, исполнитель, комментатор и упомянутый
становятся наблюдателями автоматически. Явный отказ (`DELETE`) сохраняется: автоматически больше не вернут.

## Каналы

| Канал | Адрес | Подтверждение |
|---|---|---|
| `in_app` | нет | не нужно |
| `email` | основной адрес пользователя или дополнительный | дополнительные адреса не получают ничего, пока владелец не перейдёт по ссылке из письма |
| `webhook` | https-URL | подписанный одноразовый токен отправляется POST на этот URL, его возвращают в `/notifications/channels/confirm` |

До 5 дополнительных адресов на тип канала (`MaxChannelsPerUserKind`). Подтверждение можно отправить повторно не
чаще раза в минуту.

Каналы регистрируются в `ChannelRegistry`; чтобы добавить канал (например Telegram), нужны реализация интерфейса
канала, его тип в `domain` и запись в реестре.

### Ограничения почты

`NOTIFICATION_EMAIL_PER_HOUR` (по умолчанию 30) ограничивает число писем на пользователя в час. Лишние письма
пропускаются, запись в приложении остаётся. Язык письма определяется настройкой пользователя и `Accept-Language`
(русский или английский).

### Webhook

- URL проверяется клиентом `internal/safehttp`: только публичные адреса, DNS закреплён на соединение, редиректы
  не выполняются, таймаут запроса 5 секунд.
- Тело: JSON с полями `type`, `delivery_id`, `created_at`, `summary`, `detail`, `task` или `form`, `actor`, `link`.
- Заголовки: `X-Rabbit-Hole-Event`, `X-Rabbit-Hole-Delivery`, `X-Rabbit-Hole-Timestamp`,
  `X-Rabbit-Hole-Signature`.
- Подпись: `sha256=` + hex HMAC-SHA256 от строки `<timestamp>.<тело>` с секретом канала. Проверяйте подпись и
  свежесть метки времени.
- Секрет показывается один раз при создании или ротации (`POST /notifications/channels/{id}/rotate-secret`); в базе хранится зашифрованным
  (AES-GCM).
- До 3 попыток на одно событие, очередь на 256 доставок, общий срок одной доставки 45 секунд.
- Канал отключается после `NOTIFICATION_WEBHOOK_MAX_FAILURES` (по умолчанию 10) подряд неудачных доставок.

## Окно уведомлений в приложении

- `GET /notifications` список с пагинацией, фильтры по прочитанности, `GET /notifications/unread-count`.
- `POST /notifications/read` отмечает прочитанными, `DELETE /notifications/{id}` удаляет. Общие настройки: `GET/PUT /notifications/settings`.
- Хранится не более `NOTIFICATION_MAX_PER_USER` (по умолчанию 1000) записей на пользователя; старые вытесняются.

## Realtime-лента

`POST /notifications/events/ticket` выдаёт одноразовый билет на 30 секунд, затем
`GET /notifications/events?ticket=...` открывает WebSocket. События: `notification.created`, `notification.read`,
`notification.deleted`, `notification.unread_count`. Доставка best effort: при обрыве перечитайте список через REST.
Подробно: [`realtime.md`](realtime.md).

## Известные ограничения

- Очереди диспетчера и webhook живут в памяти процесса; при аварийном падении недоставленное теряется.
- Нет повторной доставки по расписанию после исчерпания 3 попыток.
- Telegram и push на устройства не реализованы.
