# Заметки: что делать в редакторе и вне его

Черновик дизайна заметок, которые ссылаются друг на друга и хранят версии (ориентиры: Notion, Obsidian). Редактор:
[Inkbrick](https://github.com/CyberWizard6090/Inkbrick) (`0.1.0-alpha.0`, API может меняться). Документ ещё не утверждён: пункты
«Решить до начала» ниже определяют объём работ. Содержимое заметок с первой версии хранится в CRDT и редактируется совместно:
это описано отдельно в [`collab-architecture.md`](collab-architecture.md), здесь остаётся продуктовая часть (ссылки, структура, права, API).

## Как устроен Inkbrick (что уже есть)

- Документ это дерево блоков, сохраняется JSON-снимком `{version, rootId, blocks: {id: блок}, schemaVersions}`. Блок:
  `{id (UUID), flavour, parentId, children, content: [{insert, attributes}], props, meta?}`.
- `editor.serialize()`, `deserializeDocument(json, {schema})` (проверка структуры, миграции props), `repairSnapshot`.
- Инлайн-атрибуты это открытый словарь (`[key: string]: string | boolean | undefined`), известные: `bold`, `italic`, `underline`, `strike`,
  `code`, `link`, `color`, `backgroundColor`, `formula`. Формула устроена как «атом»: текст из символов-объектов `FORMULA_CHAR`, в DOM
  нередактируемый `<span data-inkbrick-formula>`, по клику открывается правка. Так же можно сделать ссылку на заметку.
- `isSafeUrl` пропускает `http(s)`, `mailto`, `tel`, **относительные пути** и якоря.
- `images.upload` / `images.rehost` загружают картинки на ваш сервер; без `upload` картинки встраиваются в документ как `data:` до 1,5 МБ.
- Движок и модель без React и DOM, работают в Node.
- Нет: ссылок между документами, обратных ссылок, версий (undo/redo только в памяти), совместного редактирования (нет CRDT, нет
  журнала операций, сохраняется снимок целиком).
- Изменения внутри редактора это объекты `Change` (`SetBlock`, `UpdateBlock`, `DeleteBlock`, `InsertChild`, `RemoveChild`, `MoveChild`) в
  транзакциях `DocumentStore.transact`. `UpdateBlock` заменяет `content` блока целиком, а его откат (`revert`) возвращает блок целиком в прежнее
  состояние. Порядок детей задаётся индексом массива `children`. Метаданные `meta` берутся из `Date.now()`. Это важно для CRDT (ниже).

## Решить до начала

1. **Ссылки.** Только `[[…]]` внутри заметок или ещё из задач и комментариев на заметки?
2. **Структура.** Плоский список с обратными ссылками (Obsidian), дерево страниц (Notion) или оба?
3. **Авторство.** Решено: заметки сразу строятся на CRDT (Yjs на клиенте, `reearth/ygo` внутри сервера), этапа с одним автором и
   оптимистичной блокировкой нет. Офлайн позже. Подробности и этапы K0–K6 в [`collab-architecture.md`](collab-architecture.md).
4. **Вид ссылки.** Вариант A: обычный `link` с относительным адресом `/n/<id>`. Вариант B: свой атом `noteRef` (раздел «Редактор»).
   A делается за день и проходит через вставку, экспорт и проверки без правок, но подпись ссылки остаётся такой, какой её ввели;
   B показывает актуальное название и умеет «заметка удалена», но требует правок в нескольких местах. Рекомендую начать с A и перейти на B,
   когда понадобятся живые названия.

## Что делать в редакторе (Inkbrick)

Для варианта A почти ничего, кроме выбора заметки и клика. Для B:

| Задача | Где | Подробности |
|---|---|---|
| Модель | `packages/document/src/model/InlineNode.ts` | атрибут `noteRef` (id заметки, строка ограниченной длины и формата UUID); блок `anchor` (id блока в заметке) необязателен |
| Проверка снимка | `packages/document/src/serialization`, `schema` | неизвестный атрибут допустим, но проверьте формат `noteRef` и размер; `repairSnapshot` должен его не ломать |
| Отображение | `packages/react/src/editing/renderInline.ts` | `renderNode` знает только фиксированные атрибуты: добавить ветку для `noteRef` (нередактируемый `<span data-inkbrick-note-ref data-note-id>`, как у формулы) и стиль в `@inkbrick/styles` (`data-inkbrick-*`, токены) |
| Название | опция редактора `notes.resolve(id)` | редактор не знает заметок: приложение даёт хук, который по id возвращает `{title, exists, accessible}`; недоступная заметка выглядит как «заметка недоступна» и не раскрывает название |
| Клик | `packages/react/src/editing/useEditorInput.ts` (`onClick`) | сейчас ловит клик по формуле и Ctrl+клик по `a[href]`; добавить событие `notes.onOpen(id)` (в режиме только чтения достаточно обычного клика) |
| Ввод | `packages/react/src/slash`, `keymap` | по вводу `[[` открыть выбор заметки (меню на основе слэш-меню: `SlashMenuController`, `syncSlashMenu`); хук `notes.search(query)` отдаёт список; выбор вставляет атом |
| Вставка из буфера | `packages/engine/src/clipboard/sanitize.ts` | `sanitizeAttributes` оставляет **только известные** атрибуты, поэтому `noteRef` пропадёт при копировании внутри редактора: добавить его в белый список с той же проверкой формата |
| Вставка HTML | `packages/react/src/clipboard/html/style.ts` | при копировании из HTML внутренняя ссылка не распознаётся; для варианта B отдавать `<a href="/n/<id>" data-note-id>` и читать обратно |
| Экспорт | `packages/document/src/adapters/markdown.ts`, `html.ts`, `plainText.ts` | Markdown: `[[Название]]` или `[Название](/n/<id>)`; HTML: `<a href data-note-id>`; текст: название; рядом с формулой уже есть образец (`isFormulaNode`) |
| Режим «только чтение» | `docs/read-only.md` | ссылка кликабельна, правка нет |
| Тесты | `packages/*/__tests__`, `tests/` (Playwright) | сохранение и загрузка, копирование и вставка между документами, undo/redo вокруг атома, экспорт, `repairSnapshot`, ввод `[[` на мобильной клавиатуре (IME), доступность (axe) |
| Документация и версия | `docs/`, `CHANGELOG.md`, `schemaVersions` | описать опцию `notes`; если меняется формат props блока, поднять `BlockSchema.version` и написать `migrate` |
| Размер | `pnpm size` | бюджет бандла ограничен (около 58 КБ gzip для React-редактора): не тянуть новых зависимостей |

Дополнительно в редакторе стоит проверить (не проверялось): сохраняются ли неизвестные инлайн-атрибуты при копировании внутри
документа, при Tab/Enter внутри списка и при слиянии блоков (разрыв и склейка узлов с одинаковыми атрибутами).

## Что делать вне редактора

### Сервер (rabbit-hole-server)

- **Таблицы** (в `000001_init_schema`, миграции до релиза правятся на месте; после релиза только новыми файлами):
  - `notes(id, workspace_id, parent_id NULL, title, content JSONB, content_text, content_format, snapshot_seq, created_by, updated_by,
    created_at, updated_at, deleted_at)`; `content` и `content_text` это снимок, который сервер собирает из CRDT-состояния, а не то, что
    прислал клиент.
  - `note_crdt_state`, `note_crdt_updates`: состояние и журнал CRDT (см. [`collab-architecture.md`](collab-architecture.md)).
  - `note_versions(id, note_id, seq, title, content JSONB, created_by, created_at, label NULL, kind)`.
  - `note_links(from_note_id, to_note_id, block_id NULL)`, PK по тройке, индекс по `to_note_id` (обратные ссылки).
  - Поиск: колонка с плоским текстом и индекс `pg_trgm`, как у задач.
- **Права**: `note.read`, `note.create`, `note.update`, `note.delete` в `domain.DefaultRoles` (таблица в `permissions.md`, тест матрицы ролей).
  Чужая и несуществующая заметка неотличимы (403), как у задач.
- **API** (все ответы типизировать в `openapi.yaml`, потом `make api-types`):
  - `GET/POST /workspaces/{id}/notes`, `GET/PATCH/DELETE /notes/{id}` (PATCH меняет название и родителя; содержимое меняется только
    через WebSocket);
  - `POST /notes/{id}/collab/ticket`, `GET /notes/{id}/collab` (совместное редактирование);
  - `GET/POST /notes/{id}/versions`, `GET /notes/{id}/versions/{n}`, `POST /notes/{id}/versions/{n}/restore` (откат применяет редактор);
  - `GET /notes/{id}/backlinks`, `GET /workspaces/{id}/notes/search?q=` и `POST /notes/resolve` (пакетное получение названий по id для хука `notes.resolve`).
- **Сохранение**: правки приходят обновлениями CRDT и пишутся в журнал; после паузы в правках сервер в одной транзакции собирает снимок,
  пишет версию (не чаще раза в N минут или по метке), пересобирает `note_links` (сам обходит документ и собирает `noteRef` и внутренние
  ссылки; данным клиента для связей не верит) и пишет запись в журнал активности.
- **Проверка содержимого**: размер обновления и состояния, разбор обновления движком. Проверку по схемам блоков делает редактор при загрузке.
  Миграции схем блоков выполняются на клиенте; старые версии хранятся как есть, не переписываются.
- **Картинки**: использовать существующие загрузки (`images`, `files`) и `images.upload`, иначе снимки версий раздуются `data:`-картинками.
- **Версии и хранение**: политика (сколько версий и как долго) в `docs/backlog.md`, чистка в `retention`; без неё история растёт бесконечно.
- **Удаление**: мягкое; ссылки на удалённую заметку остаются в `note_links` и отображаются как «заметка удалена».
- **Уведомления и активность**: события `note.created/updated/restored`, упоминание заметки по желанию.
- **Метрики и нагрузка**: размер `content`, число `note_links` на заметку (лимит), обратные ссылки с пагинацией.

### Клиент (приложение)

- Подключение `@inkbrick/*`, закреплённая точная версия, опции `images.upload`, `notes.*`.
- Транспорт совместного редактирования (билет, WebSocket, переподключение), индикатор «сохранено», курсоры соавторов.
- Страницы: список и дерево заметок, поиск, обратные ссылки, история версий (просмотр, сравнение, восстановление).
- Миграции схем при открытии (старый снимок читается через `deserializeDocument`, ошибка показывается и запускается `repairSnapshot`).
- Переводы кодов ошибок, `Accept-Language`.

## Совместное редактирование и этапы

Формат документа в CRDT, протокол, хранение, сборка снимка и ссылок, версии, лимиты и этапы K0–K6 описаны в
[`collab-architecture.md`](collab-architecture.md); мост между редактором и CRDT в репозитории Inkbrick, `docs/collab-design.md`.

Ссылки между заметками попадают в этап K4: сначала вариант A (выбор заметки по `[[`, `link` вида `/n/<id>`, клик, обратные ссылки), затем
вариант B (атом `noteRef`, живые названия, «заметка недоступна», экспорт, буфер). Поиск и `POST /notes/resolve` входят в K2 и K4.

## Риски

- Редактор в alpha: формат и API могут меняться, закрепляйте версию и пишите миграции.
- Главные риски совместного редактирования: мост в редакторе (перенос блоков, undo, IME) и зависимость от стороннего Go-порта Yjs. Мост
  проверяет прототип K0 до заморозки формата; порт проверен тестом `tests/crdt-compat`, который становится обязательным в CI.
- Заметки не выйдут раньше, чем готов мост: этапа с простым сохранением JSON нет.
- Снимок хранится целиком, поэтому длинная история тяжёлая; нужна политика хранения.
- Миграции схем блоков идут на клиенте, а сервер на Go: данные в истории могут быть в старом формате, клиент обязан уметь их открыть.
