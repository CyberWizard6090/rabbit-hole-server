# Заметки: что делать в редакторе и вне его

Черновик дизайна заметок, которые ссылаются друг на друга и хранят версии (ориентиры: Notion, Obsidian). Редактор:
[Inkbrick](https://github.com/CyberWizard6090/Inkbrick) (`0.1.0-alpha.0`, API может меняться). Документ ещё не утверждён: пункты
«Решить до начала» ниже определяют объём работ. Совместное редактирование (CRDT) вынесено в отдельный раздел и отдельные этапы: оно
нужно не в первой версии, но первая версия должна быть к нему готова (см. «Что заложить сразу»).

## Как устроен Inkbrick (что уже есть)

- Документ это дерево блоков, сохраняется JSON-снимком `{version, rootId, blocks: {id: блок}, schemaVersions}`. Блок:
  `{id (UUID), flavour, parentId, children, content: [{insert, attributes}], props, meta?}`.
- `editor.serialize()`, `deserializeDocument(json, {schema})` (проверка структуры, миграции props), `repairSnapshot`.
- Инлайн-атрибуты это открытый словарь (`[key: string]: string | boolean | undefined`), известные: `bold`, `italic`, `underline`, `strike`,
  `code`, `link`, `color`, `backgroundColor`, `formula`. Формула устроена как «атом»: текст из символов-объектов `FORMULA_CHAR`, в DOM
  нередактируемый `<span data-inkbrick-formula>`, по клику открывается правка. Так же можно сделать ссылку на заметку.
- `isSafeUrl` пропускает `http(s)`, `mailto`, `tel`, **относительные пути** и якоря.
- `images.upload` / `images.rehost` загружают картинки на ваш сервер; без `upload` картинки встраиваются в документ как `data:` до 1,5 МБ.
- Движок и модель без React и DOM, работают в Node.
- Нет: ссылок между документами, обратных ссылок, версий (undo/redo только в памяти), совместного редактирования (нет CRDT, нет
  журнала операций, сохраняется снимок целиком).
- Изменения внутри редактора это объекты `Change` (`SetBlock`, `UpdateBlock`, `DeleteBlock`, `InsertChild`, `RemoveChild`, `MoveChild`) в
  транзакциях `DocumentStore.transact`. `UpdateBlock` заменяет `content` блока целиком, а его откат (`revert`) возвращает блок целиком в прежнее
  состояние. Порядок детей задаётся индексом массива `children`. Метаданные `meta` берутся из `Date.now()`. Это важно для CRDT (ниже).

## Решить до начала

1. **Ссылки.** Только `[[…]]` внутри заметок или ещё из задач и комментариев на заметки?
2. **Структура.** Плоский список с обратными ссылками (Obsidian), дерево страниц (Notion) или оба?
3. **Авторство.** Решено: нужно одновременное редактирование (CRDT), но отдельными этапами C0–C5 после заметок, версий и ссылок. До этого один автор
   в момент времени и оптимистичная блокировка. Нужно решить только порядок: начинать ли прототип моста (C0) параллельно с серверными этапами 1–3.
4. **Вид ссылки.** Вариант A: обычный `link` с относительным адресом `/n/<id>`. Вариант B: свой атом `noteRef` (раздел «Редактор»).
   A делается за день и проходит через вставку, экспорт и проверки без правок, но подпись ссылки остаётся такой, какой её ввели;
   B показывает актуальное название и умеет «заметка удалена», но требует правок в нескольких местах. Рекомендую начать с A и перейти на B,
   когда понадобятся живые названия.

## Что делать в редакторе (Inkbrick)

Для варианта A почти ничего, кроме выбора заметки и клика. Для B:

| Задача | Где | Подробности |
|---|---|---|
| Модель | `packages/document/src/model/InlineNode.ts` | атрибут `noteRef` (id заметки, строка ограниченной длины и формата UUID); блок `anchor` (id блока в заметке) необязателен |
| Проверка снимка | `packages/document/src/serialization`, `schema` | неизвестный атрибут допустим, но проверьте формат `noteRef` и размер; `repairSnapshot` должен его не ломать |
| Отображение | `packages/react/src/editing/renderInline.ts` | `renderNode` знает только фиксированные атрибуты: добавить ветку для `noteRef` (нередактируемый `<span data-inkbrick-note-ref data-note-id>`, как у формулы) и стиль в `@inkbrick/styles` (`data-inkbrick-*`, токены) |
| Название | опция редактора `notes.resolve(id)` | редактор не знает заметок: приложение даёт хук, который по id возвращает `{title, exists, accessible}`; недоступная заметка выглядит как «заметка недоступна» и не раскрывает название |
| Клик | `packages/react/src/editing/useEditorInput.ts` (`onClick`) | сейчас ловит клик по формуле и Ctrl+клик по `a[href]`; добавить событие `notes.onOpen(id)` (в режиме только чтения достаточно обычного клика) |
| Ввод | `packages/react/src/slash`, `keymap` | по вводу `[[` открыть выбор заметки (меню на основе слэш-меню: `SlashMenuController`, `syncSlashMenu`); хук `notes.search(query)` отдаёт список; выбор вставляет атом |
| Вставка из буфера | `packages/engine/src/clipboard/sanitize.ts` | `sanitizeAttributes` оставляет **только известные** атрибуты, поэтому `noteRef` пропадёт при копировании внутри редактора: добавить его в белый список с той же проверкой формата |
| Вставка HTML | `packages/react/src/clipboard/html/style.ts` | при копировании из HTML внутренняя ссылка не распознаётся; для варианта B отдавать `<a href="/n/<id>" data-note-id>` и читать обратно |
| Экспорт | `packages/document/src/adapters/markdown.ts`, `html.ts`, `plainText.ts` | Markdown: `[[Название]]` или `[Название](/n/<id>)`; HTML: `<a href data-note-id>`; текст: название; рядом с формулой уже есть образец (`isFormulaNode`) |
| Режим «только чтение» | `docs/read-only.md` | ссылка кликабельна, правка нет |
| Тесты | `packages/*/__tests__`, `tests/` (Playwright) | сохранение и загрузка, копирование и вставка между документами, undo/redo вокруг атома, экспорт, `repairSnapshot`, ввод `[[` на мобильной клавиатуре (IME), доступность (axe) |
| Документация и версия | `docs/`, `CHANGELOG.md`, `schemaVersions` | описать опцию `notes`; если меняется формат props блока, поднять `BlockSchema.version` и написать `migrate` |
| Размер | `pnpm size` | бюджет бандла ограничен (около 58 КБ gzip для React-редактора): не тянуть новых зависимостей |

Дополнительно в редакторе стоит проверить (не проверялось): сохраняются ли неизвестные инлайн-атрибуты при копировании внутри
документа, при Tab/Enter внутри списка и при слиянии блоков (разрыв и склейка узлов с одинаковыми атрибутами).

## Что делать вне редактора

### Сервер (rabbit-hole-server)

- **Таблицы** (в `000001_init_schema`, миграции до релиза правятся на месте; после релиза только новыми файлами):
  - `notes(id, workspace_id, parent_id NULL, title, content JSONB, version INT, created_by, updated_by, created_at, updated_at, deleted_at)`;
    `version` растёт на каждое сохранение (оптимистичная блокировка).
  - `note_versions(id, note_id, version, title, content JSONB, created_by, created_at, label NULL)`.
  - `note_links(from_note_id, to_note_id, block_id NULL)`, PK по тройке, индекс по `to_note_id` (обратные ссылки).
  - Поиск: колонка с плоским текстом и индекс `pg_trgm`, как у задач.
- **Права**: `note.read`, `note.create`, `note.update`, `note.delete` в `domain.DefaultRoles` (таблица в `permissions.md`, тест матрицы ролей).
  Чужая и несуществующая заметка неотличимы (403), как у задач.
- **API** (все ответы типизировать в `openapi.yaml`, потом `make api-types`):
  - `GET/POST /workspaces/{id}/notes`, `GET/PATCH/DELETE /notes/{id}` (PATCH принимает `version`: 409 `NOTE_VERSION_CONFLICT`
    с текущей версией при расхождении);
  - `GET /notes/{id}/versions`, `GET /notes/{id}/versions/{n}`, `POST /notes/{id}/versions/{n}/restore` (создаёт новую версию);
  - `GET /notes/{id}/backlinks`, `GET /workspaces/{id}/notes/search?q=` и `POST /notes/resolve` (пакетное получение названий по id для хука `notes.resolve`).
- **Сохранение**: в одной транзакции обновить заметку, записать версию (не чаще раза в N минут или по метке), пересобрать `note_links`
  (сервер сам обходит JSON на Go и собирает `noteRef` и внутренние ссылки; данным клиента для связей не верить), записать запись в журнал активности.
- **Проверка содержимого**: размер тела (например 1–2 МБ), число блоков и глубина, корректный JSON с `rootId` и `blocks`. Полную проверку делает редактор
  при загрузке, но сервер не должен хранить мусор. Миграции схем блоков выполняются на клиенте при открытии; старые версии хранятся как есть, не переписываются.
- **Картинки**: использовать существующие загрузки (`images`, `files`) и `images.upload`, иначе снимки версий раздуются `data:`-картинками.
- **Версии и хранение**: политика (сколько версий и как долго) в `docs/backlog.md`, чистка в `retention`; без неё история растёт бесконечно.
- **Удаление**: мягкое; ссылки на удалённую заметку остаются в `note_links` и отображаются как «заметка удалена».
- **Уведомления и активность**: события `note.created/updated/restored`, упоминание заметки по желанию.
- **Метрики и нагрузка**: размер `content`, число `note_links` на заметку (лимит), обратные ссылки с пагинацией.

### Клиент (приложение)

- Подключение `@inkbrick/*`, закреплённая точная версия, опции `images.upload`, `notes.*`.
- Автосохранение с отправкой `version`, обработка 409 (показать «заметка изменилась», предложить перезагрузить или сохранить копию).
- Страницы: список и дерево заметок, поиск, обратные ссылки, история версий (просмотр, сравнение, восстановление).
- Миграции схем при открытии (старый снимок читается через `deserializeDocument`, ошибка показывается и запускается `repairSnapshot`).
- Переводы кодов ошибок, `Accept-Language`.

## Совместное редактирование (CRDT)

Цель: несколько человек правят одну заметку одновременно, без `409`, с курсорами других людей; бонус: работа офлайн с автослиянием.

### Выбор библиотеки

| Вариант | За | Против |
|---|---|---|
| **Yjs** | самый зрелый, большая экосистема (`y-websocket`, Hocuspocus, `y-protocols`, `UndoManager`, awareness), богатый текст | нет встроенного перемещения блоков в дереве; на Go только сторонние порты (ниже) |
| **Loro** | перемещаемое дерево и богатый текст «из коробки», конкурентные переносы без циклов | моложе, меньше готовых серверов; на Go есть community-привязки (`aholstenson/loro-go`), чистый Go-вариант читает формат, но стили богатого текста пока не поддерживает |
| Automerge | зрелый, хорошая модель | тяжелее, меньше готового для редакторов |

Рекомендация: **Yjs** для первого прототипа, так как вокруг него готово больше всего (протокол, провайдеры, undo, курсоры). Если перенос блоков
окажется слишком хрупким, прототип на Loro стоит сравнить, потому что ради дерева он и придуман. Решение принимается по результатам прототипа (этап C0).

### Что нужно в редакторе (Inkbrick)

Главные расхождения между устройством Inkbrick и CRDT:

1. **Состояние.** Источник правды становится CRDT-документ (например `Y.Doc`), модель Inkbrick его проекция. Нужен мост «Inkbrick ↔ CRDT» в
   отдельном пакете (`@inkbrick/collab`), чтобы ядро не зависело от библиотеки. Пакет подписывается на `store.subscribeChanges` и применяет чужие
   изменения в хранилище.
2. **Отображение модели на CRDT.**
   - `blocks`: словарь `id -> {flavour, parentId, index, props, content}`; `props` словарём, `content` как богатый текст CRDT (`Y.Text` с атрибутами: у
     формулы это символы-объекты `FORMULA_CHAR` с атрибутом `formula`, у ссылки на заметку `noteRef`).
   - **Порядок детей и перенос.** Индексный массив `children` не годится: конкурентный перенос даёт дубликаты или потерянные блоки. Хранить у блока
     `parentId` и дробный ключ порядка (`index`, строка, как fractional indexing); перенос это запись этих двух полей, конкурентные переносы разрешаются
     «последний выигрывает» без дубликатов. Остаётся риск **цикла** (A внутри B и B внутри A после двух одновременных переносов): его чинит
     детерминированная проверка при загрузке и после слияния (в Inkbrick уже есть `repairSnapshot` для циклов и сирот, нужен вариант, который
     одинаково работает на всех клиентах). Loro решает цикл сам.
   - **Корень и `children`.** Массив `children` в модели Inkbrick строится из `parentId` + `index`, а не хранится.
3. **Изменения в обе стороны.**
   - *Локальные:* `UpdateBlock` приходит с полным `content`: мост считает разницу со старым содержимым (вставки и удаления по символам и атрибутам, как делают
     `y-prosemirror` и подобные), иначе одновременная печать в одном абзаце затрёт чужие правки. `InsertChild`, `RemoveChild`, `MoveChild` из индексов
     превращаются в `parentId` + `index`.
   - *Удалённые:* нужен способ применить изменения в `DocumentStore` **не записывая их в историю** и без штампа `meta` (сейчас `DocumentWriter` наружу не
     экспортируется). Добавить `store.transactRemote(changes)`.
4. **Undo/redo.** Текущий `History` откатывает, возвращая блок целиком в прежнее состояние (`UpdateBlockChange.revert`), и **затрёт чужие правки того же
   блока**. В режиме совместной работы историю заменить на менеджер отмены CRDT (`Y.UndoManager` отменяет только свои операции). Нужна опция
   `history: 'collab'` в `Editor`.
5. **Метаданные блока.** `meta.updatedAt/By` из `Date.now()` на каждом клиенте даёт расхождения. В режиме совместной работы либо отключить `meta`, либо
   писать её как обычное поле CRDT (последний выигрывает), либо брать авторство с сервера.
6. **Выделение и курсоры.** Выделение Inkbrick это `blockId + offset`, а удалённые правки сдвигают смещения. Хранить выделение как относительные позиции
   CRDT, пересчитывать после каждого удалённого обновления; курсоры и выделения других людей через awareness (имя, цвет), отрисовка через слоты
   (`slots`, `data-inkbrick-*`).
7. **Ввод через IME.** Пока идёт композиция (обработчики `compositionstart/compositionend` в `useEditorInput.ts`), удалённые изменения этого блока
   откладывать до конца композиции. `renderInline` рисует DOM императивно, надо проверить восстановление каретки (`CaretController`) при перерисовке чужой правкой.
8. **Начальная загрузка и миграции схем.** Новый документ начинается с `Y.Doc`, созданного из JSON-снимка (`deserializeDocument`) на одном клиенте;
   миграции схем блоков (`schemaVersions`) выполнять **до** создания документа и записывать версию в CRDT. Два клиента не должны одновременно
   «инициализировать» один документ: инициализацию делает сервер или первый клиент под блокировкой.
9. **Тесты.** Детерминированный фазз-тест: N реплик выполняют случайные операции (печать, удаление, форматирование, вставка и перенос блоков, Tab/Shift+Tab,
   вставка из буфера), обмениваются обновлениями в случайном порядке и должны сойтись к одинаковому снимку, проходящему `validateSnapshot`. Отдельно:
   конкурентные переносы (циклы), удаление блока, в который кто-то пишет, undo чужих правок, IME, офлайн-слияние.
10. **Размер и версии.** Бандл: библиотека CRDT тянет десятки КБ (Yjs около 20 КБ gzip); держать мост в отдельном пакете и грузить лениво, чтобы не
    ломать бюджет `pnpm size`. Alpha-редактор: закрепить версию, описать формат в `docs/`.

Ядро (`document`, `engine`, `store`) должно остаться пригодным без CRDT: мост подключается опцией.

### Что нужно вне редактора

**Транспорт и протокол.**
- WebSocket `GET /notes/{id}/collab` с одноразовым билетом (как `POST /lists/{id}/events/ticket`): `POST /notes/{id}/collab/ticket` проверяет `note.read`
  (читатель) или `note.update` (редактор) и отдаёт билет с признаком `write`. Права перепроверяются каждые две минуты и при смене роли или удалении из
  пространства соединение закрывается (уже есть для событий: `Hub.DisconnectUser`).
- Протокол `y-websocket` / `y-protocols` (sync step 1/2, update, awareness): тогда подойдут готовые провайдеры на клиенте.
- **Права на запись.** Тип сообщения (sync update) читается без разбора CRDT, поэтому сервер **отбрасывает** обновления соединений без `write`.
  Содержимое обновления сервер без CRDT-движка проверить не может: злонамеренный редактор способен испортить документ. Защита: версии и откат,
  лимиты, журнал активности.
- Лимиты: размер сообщения, число соединений на заметку и на пользователя, частота обновлений (по соединению), размер документа.

**Хранение.**
- `note_crdt_updates(note_id, seq BIGSERIAL, update BYTEA, author_id, created_at)` (журнал) и `note_crdt_state(note_id, state BYTEA, up_to_seq,
  updated_at)` (сжатое состояние). Новый клиент получает состояние плюс хвост журнала.
- **Сжатие** (слияние журнала в состояние) требует CRDT-движка на сервере. Без него журнал растёт бесконечно, поэтому либо серверный движок
  (ниже), либо клиент периодически присылает полное состояние, а сервер заменяет им журнал до `seq` (это даёт любому редактору право переписать
  документ целиком, как и обновление, но проверять нечем).
- Копии и восстановление: состояние в `BYTEA` входит в `pg_dump`; поддержать проверку целостности (загрузка состояния при старте заметки).

**Несколько реплик сервера.** Хаб событий сейчас в памяти процесса. Обновления одной заметки должны доходить до всех реплик: `LISTEN/NOTIFY`
Postgres (ограничение размера сообщения, поэтому по уведомлению читать `seq` из журнала) либо маршрутизация по заметке на одну реплику (хеш `note_id`).
Выбрать до реализации; для одной реплики хватит памяти процесса.

**Серверный движок CRDT: три пути (решение за вами).**

| Путь | Что это | Плюсы | Минусы |
|---|---|---|---|
| 1. Ретранслятор на Go | Go хранит и раздаёт бинарные обновления, содержимого не понимает | проще всего, один сервис | нет сжатия на сервере, нельзя проверить содержимое и получить снимок |
| 2. Go-порт Yjs | библиотека `ygo` (`reearth/ygo`, форк `Deln0r/ygo`) или `CivNode/yjs-go` для разбора, слияния и сжатия | один сервис, снимок и ссылки собирает Go | порты молодые; совместимость с Yjs заявлена авторами, мы её не проверяли; до версии 1.0 API может меняться; для Loro чистый Go-вариант не поддерживает стили богатого текста |
| 3. Сервис на Node | отдельный процесс (Hocuspocus или свой на `y-websocket`) с движком Inkbrick | единственный путь, где рядом живёт `deserializeDocument` и проверка содержимого; зрелый Yjs | второй процесс в эксплуатации, нужна связь с Go (авторизация, права, запись) |

Рекомендация: на этапе прототипа путь 1 (меньше всего работы), на этапе сжатия и проверки содержимого решать между 2 и 3 по результатам теста
совместимости выбранного Go-порта с настоящим клиентом `y-websocket` и по нагрузке. Тест совместимости (клиент Yjs против Go-сервера, V1 и V2 формат,
большие документы, переподключение) нужно написать до выбора.

**Производные данные (ссылки, поиск, версии).** Они строятся из JSON-снимка документа, а источник правды теперь CRDT. Кто делает снимок:
- *клиент* присылает JSON после паузы в правках (быстро, но клиент может прислать снимок, не совпадающий с CRDT-состоянием; серверу годится как кэш для
  поиска и ссылок, но не как правда);
- *сервер* (путь 2 или 3) собирает снимок из CRDT-состояния сам. Предпочтительно, когда доступно.
Ссылки между заметками (`note_links`) собирать из снимка на сервере, как и в плане без CRDT.

**Версии.** Остаются `note_versions` со снимком JSON (метка, автор, время). Откат создаёт **новые правки** поверх текущего состояния (разница между снимком
и текущим документом), а не подменяет CRDT-историю. Для просмотра старого состояния достаточно JSON.

**Наблюдаемость.** Метрики: открытые соединения заметок, размер журнала, задержка сжатия, отброшенные обновления без `write`, размер состояния (в `alerts.yml`:
рост журнала и отставание сжатия). Журнал активности: `note.updated` не на каждое обновление, а по пачкам (раз в N минут на автора).

**Эксплуатация.** Обновление протокола и формата между версиями редактора и сервера: клиент и сервер должны согласовывать версию формата заметки
(`content_format`, `crdt_schema`); несовместимый клиент получает ошибку и просьбу обновить приложение.

### Что заложить сразу (в первых PR, ещё без CRDT)

- Колонка `content_format` у заметки (`inkbrick-json`; позже `inkbrick-crdt-yjs`) и версия формата.
- Идентификаторы заметок и блоков это неизменяемые UUID, не ссылки по индексу.
- В таблице заметок `content` это снимок (кэш), а не единственный источник правды: так позже можно добавить `crdt_state` рядом.
- API сохранения изолировать за одной операцией сервиса (`SaveContent`), чтобы подменить оптимистичную блокировку на приём обновлений CRDT.
- Билеты WebSocket для заметок делать по образцу уже существующих (отдельный маршрут `ticket`), с признаком `write`.
- В редакторе: подписку на изменения (`subscribeChanges`) и сериализацию держать за интерфейсом, который мост сможет подменить.

## Этапы (по PR)

1. **Заметки и версии.** Таблицы, права, CRUD, версии, оптимистичная блокировка, проверка размера. Без ссылок. (сервер)
2. **Вариант A ссылок.** Выбор заметки по `[[`, вставка `link` вида `/n/<id>`, клик, разбор внутренних ссылок на сервере, `note_links`, обратные ссылки. (редактор + сервер)
3. **Поиск и пакетное разрешение названий.** `search`, `resolve`. (сервер)
4. **Вариант B ссылок.** Атом `noteRef`, живые названия, «заметка недоступна», экспорт, буфер. (редактор)
5. **Политика версий.** Лимиты, чистка, метки версий. (сервер)
6. **Позже:** дерево страниц, ссылки на блоки, ссылки из задач, общий доступ.

### Этапы совместного редактирования (после этапов 1–3)

C0. **Прототип моста в Inkbrick без сервера.** Пакет `@inkbrick/collab`: две копии редактора на одной странице, обмен обновлениями в памяти; `transactRemote`,
отображение модели на CRDT, перенос блоков с защитой от цикла, `history: 'collab'`, относительное выделение, фазз-тест сходимости. Критерий: фазз-тест зелёный,
переносы и IME не ломаются. Решение Yjs или Loro.

C1. **Сервер-ретранслятор на Go.** Билеты, WebSocket, `y-websocket`-протокол, отбрасывание обновлений без `write`, журнал `note_crdt_updates`, лимиты. Тест
совместимости с настоящим клиентом.

C2. **Состояние и сжатие.** Выбор пути 2 или 3 по результатам тестов, `note_crdt_state`, сжатие, сборка JSON-снимка на сервере, `note_links` и поиск из него.

C3. **Присутствие.** Awareness: курсоры, имена, цвета, «кто сейчас в заметке».

C4. **Версии и откат поверх CRDT**, метрики и алерты, несколько реплик (LISTEN/NOTIFY или маршрутизация).

C5. **Офлайн.** Локальное хранение обновлений (IndexedDB), повторная отправка, конфликты прав (человека удалили, пока он был офлайн).

## Риски

- Редактор в alpha: формат и API могут меняться, закрепляйте версию и пишите миграции.
- Без CRDT одновременное редактирование не поддерживается: при двух авторах будут конфликты 409. С CRDT главные риски: перенос блоков (циклы, дубликаты), undo, IME,
  размер журнала и невозможность проверить содержимое обновления без серверного движка.
- Go-порты Yjs молодые: совместимость заявлена авторами, не проверена нами; до выбора нужен тест против настоящего клиента.
- Снимок хранится целиком, поэтому длинная история тяжёлая; нужна политика хранения.
- Миграции схем блоков идут на клиенте, а сервер на Go: данные в истории могут быть в старом формате, клиент обязан уметь их открыть.
