# Производительность

Результаты нагрузочного прогона и способ его повторить. Цифры сняты на тестовой машине, а не на проде: относитесь к ним
как к сравнению сценариев между собой и до/после правок.

## Как повторить

```bash
createdb rh_load                      # имя обязательно содержит "load": утилита стирает схему этой базы
make loadtest DB='host=127.0.0.1 user=postgres password=... dbname=rh_load sslmode=disable'
```

Утилита `cmd/loadtest` поднимает сервер в процессе, пересоздаёт схему, регистрирует пользователей через API, заполняет базу
SQL-ом и несколько минут гоняет смешанную нагрузку по HTTP. Полезные флаги:

| Флаг | Смысл |
|---|---|
| `-reset` | стереть схему, мигрировать и заполнить (для повторного прогона на тех же данных: `-skip-seed`) |
| `-tasks 200000` | число задач |
| `-users 40` | число пользователей (все участники одного пространства) |
| `-duration 60s`, `-concurrency 32` | длительность и число виртуальных пользователей |
| `-only текст`, `-exclude текст` | оставить или убрать сценарии по части имени |
| `-hot-tasks 500000` | добавить столько задач в один список и направить все запросы списков в него |

В конце утилита печатает по каждому сценарию число запросов, rps, ошибки и p50/p95/p99, задержку очереди outbox, таблицы с
наибольшим чтением через последовательное сканирование и запросы дольше 100 мс. Планы запросов можно получить через
`auto_explain` для базы (`ALTER DATABASE rh_load SET session_preload_libraries = 'auto_explain'`, затем
`auto_explain.log_min_duration` и `auto_explain.log_analyze`) и прочитать из журнала PostgreSQL.

Лимиты по IP в прогоне не мешают: каждый запрос получает случайный `X-Forwarded-For` (прокси `127.0.0.1` доверенный), так
что работает и общий PostgreSQL-лимитер.

## Условия прогона

- 4 ядра, PostgreSQL 16 с настройками по умолчанию, генератор нагрузки и сервер на той же машине: цифры занижены.
- 12 списков, 120 000 задач (по 10 000 в списке), 30 000 комментариев, 60 000 записей активности, около 4 000 уведомлений,
  40 пользователей. Заголовки задач: слово из словаря и два случайных hex-слова, чтобы поиск по «конкретному слову» был
  избирательным.
- Смесь: списки задач (три вида), карточка задачи, создание и правка задачи, комментарий, поиск, лента активности, уведомления,
  публичная отправка формы, вход.

## Находки

### 1. Поиск по пространству съедал процессор (P0, исправлено)

`GET /workspaces/{id}/search` на 120 000 задач и 30 000 комментариев:

| Условие | До исправления | После |
|---|---:|---:|
| один пользователь, «конкретное слово» | около 1,0 с | единицы миллисекунд на запрос к индексу |
| 32 пользователя в общей смеси, конкретное слово (p50 / p95) | 16 415 / 22 720 мс | 132 / 256 мс |
| 32 пользователя в общей смеси, частое слово (p50 / p95) | 20 148 / 21 977 мс | 1 551 / 4 891 мс |

Причина по `auto_explain`: запрос соединял `tasks`, `task_comments` и `task_checklist_items` и ставил условие
`ILIKE '%…%' OR 'слово' <% колонка` сразу по заголовку и описанию. Планировщик не использовал GIN-индексы `pg_trgm` для
такого ИЛИ, читал `tasks` и `task_comments` целиком и вычислял сходство для каждой строки (около 70 мкс на строку).
Поиск занимал все ядра и в 2–4 раза замедлял остальные запросы.

Исправление: для каждого источника сначала строится набор кандидатов отдельными простыми условиями (`ILIKE` и `<%` по
каждой колонке, объединение `UNION`), и каждое из них идёт по своему индексу. Только кандидаты соединяются со списками и
пространствами и получают оценку. Результаты и порядок не менялись.

Остаток: очень частое слово (12,5 % задач) приходится оценивать по всем совпадениям, около 15 000 строк, это 1–5 секунд
под нагрузкой. Ограничение числа кандидатов изменило бы точные итоги и глобальный порядок, это продуктовое решение.

### 2. Блокировка строки списка при записи задач (P1, исправлено)

`SELECT id FROM lists WHERE id = ? FOR UPDATE` встречался 117 раз дольше 100 мс (максимум 531 мс) при 32 пользователях и
12 списках: все изменения задач одного списка выстраивались в очередь. Теперь блокировки разные по силе:

| Операция | Блокировка списка | Конфликтует с |
|---|---|---|
| правка и удаление задачи | `FOR KEY SHARE` | перенос, удаление списка, замена статуса |
| создание задачи (выбор позиции) | `FOR NO KEY UPDATE` | другое создание, перенос |
| перенос задачи, удаление списка, замена статуса | `FOR UPDATE` | всё перечисленное |

Правки больше не ждут друг друга и создание задач, а параллельные создания по-прежнему идут по очереди, поэтому позиции
не повторяются. После изменения ожиданий блокировки дольше 100 мс в прогоне нет (было 117, затем 53 только на создании).
Задержки правки и создания при 32 пользователях почти не изменились, потому что четыре ядра заняты полностью:
выигрыш в блокировках виден по их отсутствию, а не по p95.

### 3. Список задач на очень большом списке (проверено)

В одном списке 517 000 живых задач (прогон с `-hot-tasks 500000`, другие списки по 17 000), 16 пользователей, только запросы
списков. Строка «шесть страниц подряд» — шесть последовательных запросов по keyset-курсору, остальные строки — первая страница:

| Запрос | p50 | p95 |
|---|---:|---:|
| новые сверху | 26 мс | 70 мс |
| сортировка по приоритету и сроку с фильтрами | 39 мс | 93 мс |
| текстовый фильтр списка | 20 мс | 60 мс |
| фильтр по статусу | 29 мс | 76 мс |
| фильтр по исполнителю | 108 мс | 271 мс |
| с общим числом (`with_total=true`) | 117 мс | 260 мс |
| шесть страниц подряд по курсору | 184 мс | 281 мс |

Один пользователь без конкурентов: первая страница 3,5 мс, сортировка с фильтрами 9 мс, общее число 90 мс. Пагинация по
курсору не деградирует с глубиной, обычные запросы остаются в индексах `(list_id, …)`.

Что стоит знать:

- Подсчёт `with_total=true` читает все живые задачи списка (около 100 мс на 517 000), поэтому он включается по запросу,
  а не всегда.
- Фильтр по исполнителю у пользователя, у которого в огромном списке нет ни одной задачи, обходит весь список в порядке
  сортировки (планировщик не может знать, что совпадений нет): 120–430 мс одиночно и около 2 с при 16 параллельных запросах.
  Для обычного распределения исполнителей запрос заканчивается на первых совпадениях. Менять запрос ради этого угла
  я не стал: принудительное соединение «от исполнителя» ухудшило бы случай, когда у пользователя много задач.
- Индекс по `task_assignees (user_id)` уже есть, для списков до десятков тысяч задач планировщик сам выбирает соединение
  от исполнителя (7 мс).

### 3a. Каскадное удаление задач: нехватка индекса (исправлено)

При удалении 500 000 задач одним запросом база четверть часа занималась проверками внешних ключей. `EXPLAIN ANALYZE` показал,
что 2 000 удалений тратят 5 087 мс на ограничение `fk_task_comments_task`: единственный индекс `task_comments (task_id, id)` был
частичным (`WHERE deleted_at IS NULL`) и не подходил проверке внешнего ключа, она читала всю таблицу комментариев для
каждой удаляемой задачи. После замены индекса на полный те же 2 000 удалений занимают 88 мс (в 60 раз быстрее).

Тем же способом добавлены недостающие индексы внешних ключей на больших таблицах: `files (task_id)`,
`notifications (task_id)` и `notifications (actor_id)` (частичные по `IS NOT NULL`, этого достаточно для проверок
`= $1`). Приложение удаляет задачи мягко, но физическое удаление происходит при каскадах и при ручной очистке.

### 4. Остальное в порядке

- Последовательные сканирования идут по крошечным таблицам (права, роли, участники, списки), планировщик выбирает их сам:
  это не проблема. Таблицу `tasks` в обычном режиме читают по индексам (2 Seq Scan на 1,4 млн индексных).
- Вход стоит 150–320 мс из-за argon2 по замыслу; параллелизм ограничен `AUTH_HASH_CONCURRENCY`.
- Общие лимиты в PostgreSQL выдерживают сотни обращений в секунду; единичные записи `rate_limit_windows` по 400 мс видны только
  при полной загрузке процессора.
- Очередь outbox не накапливает мёртвых событий, задержка обработки измеряется секундами.

## Что дальше

1. Решить, нужно ли ограничивать число кандидатов поиска для очень частых слов (находка 1, остаток).
2. Решить, нужен ли отдельный запрос для фильтра по исполнителю в огромных списках (находка 3).
3. Повторить прогон на машине без совмещения генератора и сервера и с настроенным PostgreSQL (`shared_buffers`,
   `work_mem`), чтобы получить абсолютные цифры.
