# Блокноты и документы

Блокнот лежит на уровне рабочего пространства (рядом с пространствами, не внутри них) и хранит документы. Документ это
совместно редактируемый текст редактора Inkbrick. Сервер хранит его как байты Yjs; слияние правок делают клиенты. Целое состояние (снимок) сервер разбирает пакетом `internal/editor` и отклоняет, если оно не документ (см. «Проверка документа»).

```
workspace ─┬─ spaces → lists → tasks
           └─ notebooks → documents → (снимок Yjs + обновления)
```

## Права

`doc.read`, `doc.create`, `doc.update`, `doc.delete` (см. [`permissions.md`](permissions.md)). Owner, Admin и Member имеют все четыре,
Guest только `doc.read`. Права проверяет middleware по идентификатору блокнота или документа (`inNotebook`, `inDocument`):
удалённый, чужой и несуществующий идентификатор дают одинаковый 403.

## Маршруты

| Маршрут | Право | Что делает |
|---|---|---|
| `GET/POST /workspaces/{id}/notebooks` | read / create | список и создание блокнотов (до 200 на пространство) |
| `GET/PATCH/DELETE /notebooks/{id}` | read / update / delete | блокнот; удаление уносит документы той же транзакцией |
| `GET/POST /notebooks/{id}/documents` | read / create | список (`page`, `limit`) и создание документов (до 5 000 в блокноте) |
| `GET/PATCH/DELETE /documents/{id}` | read / update / delete | метаданные; PATCH меняет `title`, `position`, `notebook_id` (перенос в блокнот того же пространства) |
| `GET /documents/{id}/state` | read | снимок и обновления после него: всё, чтобы открыть документ |
| `POST /documents/{id}/updates` | update | принять одну правку клиента (обновление Yjs) |
| `POST /documents/{id}/snapshot` | update | заменить историю сжатым состоянием |
| `GET /documents/{id}/blocks/activity` | read | кто создал и кто последним правил блок |

## Хранение

- `document_snapshots`: одно сжатое состояние на документ (`upto_seq` номер последнего вошедшего в него обновления).
- `document_updates`: обновления после снимка, номера `seq` подряд (1, 2, 3, ...). Номер выдаётся под блокировкой строки документа
  (`documents.update_seq`), поэтому правки одного документа упорядочены и номера не повторяются и не теряются.
- Новый документ получает начальное состояние от сервера (`internal/collab/initial_state.bin`: страница, заметка, пустой абзац),
  а не от первого клиента, который его откроет. Файл делает пакет Inkbrick `@inkbrick/collab` (тест `initialState`).

## Как клиент открывает и правит документ

1. `GET /documents/{id}/state`: применить `snapshot`, затем каждое обновление из `updates` по порядку (`Y.applyUpdate`).
2. Каждую локальную транзакцию Yjs отправлять `POST /documents/{id}/updates` с `update` (base64) и `touched` (id изменённых блоков).
3. Чужие правки приходят опросом `GET /state` или (позже) по WebSocket. Обновления Yjs коммутативны: порядок применения не важен.
4. Если `needs_compaction` равно `true` (после снимка накопилось 500 обновлений), клиент собирает состояние и отправляет его в `/snapshot`
   с `upto_seq` равным номеру последнего применённого обновления. Снимок «из будущего» или «из прошлого» даёт 409
   `DOCUMENT_SNAPSHOT_CONFLICT`.

Лимиты: обновление до 512 КиБ (413 `DOCUMENT_UPDATE_TOO_LARGE`), состояние до 8 МиБ (413 `DOCUMENT_STATE_TOO_LARGE`), 600 обновлений
в минуту и 20 снимков в минуту на пользователя.

## Кто редактировал блок

Автор правки это всегда пользователь из токена, а не поле от клиента. Клиент сообщает только список `touched` (до 200 id блоков,
каждый до 100 символов). По нему сервер ведёт `document_block_activity`: `created_by` (кто первым тронул блок), `last_edited_by` и
`last_edited_at`. Метаданные Inkbrick `meta` для этого не используются: в совместном режиме время и автор клиента недостоверны.

Сервер проверяет обновление, но не определяет по нему, какие блоки оно изменило, поэтому `touched` пишет клиент, и он может приписать правку не тому блоку. Это допустимо внутри документа, где у
пользователя и так есть право записи. Сверять `touched` с самим обновлением можно (сервер уже применяет обновления к копии документа), но это пока не сделано.

## Комната документа (WebSocket)

Открытый документ можно держать на WebSocket: правки других людей приходят сразу, и видно, кто сейчас в документе. Комната двусторонняя
(`internal/collab`), в отличие от односторонних лент задач (`internal/realtime`), но использует те же одноразовые билеты и проверки прав.

```
POST /documents/{id}/events/ticket           (doc.read)  → ticket, действует ~30 с, один раз, только для этого документа
GET  /documents/{id}/events?ticket=…&since=N             → WebSocket
GET  /documents/{id}/presence                (doc.read)  → кто в документе (по людям, не по вкладкам)
```

`since` это номер последнего обновления, которое уже есть у клиента (из `GET /state`). Сервер сначала подписывает соединение на комнату,
потом читает из БД всё после `since`, поэтому между `GET /state` и сокетом нет щели; повторы безвредны, обновления Yjs идемпотентны.

Кадры это JSON-сообщения, обновления Yjs в base64:

| От клиента | Что делает |
|---|---|
| `{"type":"update","update":"…","touched":["blockId"],"ref":"1"}` | сохранить правку (как `POST /updates`), остальным разослать, отправителю `ack` |
| `{"type":"awareness","state":{…}}` | курсор и выделение; до 4 КиБ; `null` убирает состояние |
| `{"type":"sync","since":42}` | прислать обновления после 42 |

| От сервера | Когда |
|---|---|
| `ready` | первый кадр: `conn`, `user`, `can_write`, `peers` (кто уже здесь, с их состоянием) |
| `update` | правка другого клиента или правка по REST: `seq`, `user_id`, `update` |
| `synced` | конец догоняющей отправки (`last_seq`) |
| `resync` | история сжата за `since`: заново загрузить `GET /state` |
| `ack` | своя правка сохранена: `ref`, `seq` |
| `peer_joined` / `awareness` / `peer_left` | присутствие |
| `error` | запрос отклонён, соединение живо: `FORBIDDEN`, `RATE_LIMITED` (с полем `retry_after` в секундах: правку нужно отправить снова после паузы), `INVALID_MESSAGE`, `INVALID_UPDATE`, `UPDATE_TOO_LARGE`, `AWARENESS_TOO_LARGE`, `INTERNAL` |

- **Кто есть кто.** Поле `user` во всех кадрах присутствия ставит сервер по билету (только публичные поля). Что бы клиент ни написал в
  `state`, подменить пользователя нельзя.
- **Закрытие.** Соединения закрываются сразу, не дожидаясь следующей правки или перепроверки:

  | Событие | Что получает клиент | Что делает клиент |
  |---|---|---|
  | документ удалён (`DELETE /documents/{id}`) или удалён его блокнот | закрытие 1001, причина `document deleted` | не переподключается |
  | участника убрали из пространства, сменили ему роль, пространство удалено, выход со всех устройств, смена пароля | закрытие 1001, причина `access changed` | переподключается с новым билетом: сервер отказывает (401/403) или отдаёт новые права (`can_write`) |
  | доступ пропал без уведомления (перепроверка каждые 2 минуты) | закрытие 1008, причина `access revoked` | не переподключается |
  | медленный клиент | закрытие 1008, причина `client too slow` | переподключается с `since` |
  | кадр клиента больше 1 МиБ (`MaxFrameBytes`) | закрытие 1009, причина `frame too large` | не переподключается и не шлёт тот же кадр снова: остаток сообщения нельзя пропустить, не прочитав, поэтому соединение закрывается (кадр `error` `UPDATE_TOO_LARGE` приходит только для правки, прошедшей по размеру кадра, но превысившей лимит правки) |
  | остановка сервера | закрытие 1001, причина `server shutting down` | переподключается |

  Затрагиваются только соединения этого пользователя или этого документа: остальные участники остаются в комнате.
- **Читатели.** Гость с `doc.read` получает правки и присутствие, но его `update` получает `error FORBIDDEN`. Права перепроверяются каждые
  2 минуты: удалённого из пространства отключают с кодом 1008 (`access revoked`), потерянное право записи снимается сразу.
- **Медленный клиент** (очередь из 256 кадров переполнена) отключается с 1008 `client too slow` и подключается заново с `since`.
- **Нагрузка.** До 100 соединений на документ и 20 на пользователя, кадр не больше 1 МиБ, до 50 правок в секунду на соединение (всплеск
  вдвое), состояние курсора рассылается не чаще раза в 50 мс (быстрые состояния склеиваются, уходит последнее). Каждая правка пишется в БД
  отдельной записью.
- **Один процесс.** Комнаты лежат в памяти процесса. При нескольких процессах все соединения одного документа нужно направлять на один
  (например, по хешу `document_id` на балансировщике); без этого люди в разных процессах не увидят друг друга и друг друга правок до
  следующего `sync`. Число соединений комнат входит в метрику WebSocket-соединений.

## Чего здесь ещё нет

- Серверный JSON-снимок документа (правила проекции 1–3).
- Realtime-события в ленте блокнота (создан, переименован, удалён документ).

## Проверка документа (`internal/editor`)

`POST /documents/{id}/snapshot` заменяет всю историю, поэтому присланное состояние сначала применяется к пустому документу (`ygo`)
и проверяется. Ответ 400 `VALIDATION_FAILED` с полем `state` и причиной `INVALID_VALUE`, если:

- байты не разбираются как обновление Yjs или ссылаются на данные, которых в них нет;
- нет `meta.format` равного 1 или `meta.rootId`;
- корневого блока нет, он неверной формы или его flavour не имеет роли `root`;
- блоков больше 50 000.

Нарушения схемы не отклоняются: два клиента могут создать их одновременной правкой, и каждый клиент одинаково исправляет их при проекции
(правило 4 в `@inkbrick/collab`). Они возвращаются в `Report.Issues` (неизвестный flavour, блок без родителя, `block:list` внутри
`block:paragraph`), пока для будущего логирования и метрик.

Правила вложенности лежат в `internal/editor/schema.json`. Файл не пишется вручную: его строит Inkbrick
(`packages/document/schema/blocks.json`, тест `exportSchema.test.ts` следит, чтобы он не отставал от кода).
После смены схемы в Inkbrick:

```bash
UPDATE_SCHEMA_JSON=1 pnpm vitest run packages/document/__tests__/exportSchema.test.ts
cp packages/document/schema/blocks.json ../rabbit-hole-server/internal/editor/schema.json
```

### Проверка каждого обновления

Перед записью `/updates` и кадр `update` проходят `editor.Checker`: обновление применяется к копии документа в памяти сервера, и
после него документ должен открываться (формат 1, корневой блок страницы, не больше 50 000 блоков). Иначе ответ 400 / кадр
`error` `INVALID_UPDATE`, обновление не записывается и не рассылается. Нарушения схемы не отклоняются, как и в снимке.

- Копия держится для 64 последних правленных документов (`editor.DefaultCachedDocuments`) и считается кэшем: она сбрасывается при любой
  ошибке записи, при отказе, при чужой записи (разрыв в номерах `seq`), при смене снимка и при удалении документа.
- Документ, который уже был сломан до появления проверок, не проверяется по структуре (иначе нельзя было бы ничего дописать), только по
  разбору байтов.
- Стоимость: одна печатная буква на документе в 2 000 блоков (около 1 МиБ состояния) проверяется за ~0,08 мс, на 20 000 блоков
  (около 10 МиБ) за ~1,3 мс. Первая правка после простоя загружает документ: ~1 мс на 100 блоков, ~22 мс на 2 000, ~230 мс на 20 000.
  Память: около 4 КиБ на 1 КиБ состояния (документ в 2 000 блоков ≈ 4 МиБ, в 20 000 ≈ 41 МиБ), то есть 64 документа среднего
  размера занимают порядка сотен МиБ в худшем случае.
- Обновление, которое не разбирается, отклоняется до обращения к копии. Каждое отклонённое обновление списывает с бюджета пользователя 20
  правок, чтобы повторными отправками нельзя было заставлять сервер перезагружать документ.
- Лимит 600 обновлений в минуту общий для пользователя: REST и все его сокеты. На сокете по-прежнему действует и лимит 50/с на
  соединение. Клиент объединяет быстрые правки в один кадр (раз в 150 мс), поэтому обычная печать далеко от лимита.

### Сжатие истории

Когда после снимка накопилось 200 обновлений (`service.DefaultCompactAfter`), сервер в фоне сжимает историю сам, клиенту ничего делать не нужно:
читает снимок и обновления, собирает из них документ, кодирует его заново (это убирает удалённое содержимое) и заменяет историю снимком,
который покрывает ровно прочитанные обновления. Обновления, записанные за это время, сохраняют свои номера.

- Сжатие идёт по одному на документ и никогда не ломает правку, которая его запустила.
- История остаётся как есть, если что-то необычно: обновление не разбирается или ждёт данных, которых нет в истории, документ не открылся бы,
  результат больше 8 МиБ. Это только оптимизация, и пропустить её безопасно.
- Клиент, который последний раз видел обновление старше снимка, при подключении получает кадр `resync` и заново читает `GET /state`.
- `needs_compaction` в `GET /state` остаётся для клиентов, но при работающем сжатии сервера он не появляется (порог 500 выше порога сжатия 200).
  Клиентский `POST /snapshot` по-прежнему работает и проверяется так же, как раньше.
- Стоимость: чтение истории и сборка документа, то есть как первая загрузка документа (~22 мс на 2 000 блоков), раз в 200 правок, в фоне.
