# Совместная работа над заметками: архитектура

Проект, ещё не реализован. Описывает, как несколько человек одновременно редактируют одну заметку, как это хранится и как
из этого получаются ссылки между заметками, поиск и версии. Продуктовая часть заметок (список, дерево, ссылки `[[…]]`, права)
описана в [`notes-design.md`](notes-design.md); редакторная часть (мост между Inkbrick и CRDT) в репозитории Inkbrick,
`docs/collab-design.md`.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Порядок работ | Заметки сразу на CRDT, без этапа «JSON и 409» | сохранение, автосохранение на клиенте и перенос данных не пишутся дважды |
| Библиотека | Yjs на клиенте, формат обновлений V1 | самая зрелая экосистема: протокол синхронизации, awareness, менеджер отмены |
| Серверный движок | Go-порт [`reearth/ygo`](https://pkg.go.dev/github.com/reearth/ygo) внутри `rabbit-hole-server` | один сервис; сервер сам сжимает журнал, собирает снимок, ссылки и поиск; проверено тестом (ниже) |
| Источник правды | CRDT-состояние заметки в PostgreSQL; JSON-снимок это производный кэш | снимок всегда можно пересобрать, обратное неверно |
| Офлайн | Не в первой версии, но путь не закрыт | протокол и хранение его допускают, нужен только локальный склад на клиенте |
| Реплики сервера | Одна, как сейчас у realtime; схема хранения готова к нескольким | хаб и билеты уже живут в памяти процесса ([`realtime.md`](realtime.md)) |

Запасной путь для серверного движка: отдельный сервис на Node с эталонным Yjs. Чтобы переход был возможен, весь код, который
знает о `ygo`, живёт в одном пакете за интерфейсом (`internal/collab/ydoc`), а остальной сервер видит только байты и снимки.

## Общая схема

```
Браузер                                        rabbit-hole-server                         PostgreSQL
┌───────────────────────────┐   REST    ┌────────────────────────────────┐
│ приложение                │──────────▶│ заметки: метаданные, билет,     │──────▶ notes, note_links,
│  ├ Inkbrick Editor        │           │ версии, обратные ссылки, поиск  │        note_versions
│  ├ @inkbrick/collab (мост)│           ├────────────────────────────────┤
│  │   store ⇄ Y.Doc        │   WS      │ комната заметки (в памяти):     │
│  └ транспорт (y-protocols)│◀─────────▶│  ygo-документ, соединения,      │──────▶ note_crdt_updates (журнал)
└───────────────────────────┘  бинарные │  права, лимиты, awareness       │        note_crdt_state (сжатое)
                                кадры   ├────────────────────────────────┤
                                        │ сборщик: снимок JSON, текст,    │──────▶ notes.content, content_text,
                                        │ ссылки, версии (после паузы)    │        note_links, note_versions
                                        └────────────────────────────────┘
```

Содержимое заметки меняется **только** через WebSocket. REST отдаёт готовый снимок для чтения и работает с метаданными
(название, родитель, удаление). Запроса «сохранить содержимое» и ошибки `NOTE_VERSION_CONFLICT` нет.

## Формат документа (`inkbrick-yjs`, версия 1)

Это контракт между мостом в Inkbrick и сервером. Оба читают его одинаково, поэтому правила ниже закрепляются общими
тестовыми данными (обновление в base64 → ожидаемый снимок), которые прогоняют и TypeScript, и Go. Формат принадлежит редактору:
при расхождении верен текст в Inkbrick `docs/collab-design.md`, здесь его копия.

```
Y.Doc
├ meta:   Y.Map   { format: 1, rootId, schemaVersions: { flavour: n } }
└ blocks: Y.Map   blockId →
          Y.Map   { flavour: string,
                    place:   { p: parentId, k: ключ порядка },   // одно значение, пишется целиком
                    props:   Y.Map (ключ → JSON-значение),
                    text:    Y.Text }                            // есть у каждого блока, даже без текста
```

| Часть | Правило | Зачем так |
|---|---|---|
| Порядок и вложенность | у блока `place = {p, k}`; `children` родителя это его блоки, отсортированные по `(k, blockId)` | массив `children` при одновременных переносах даёт дубликаты и потери; запись одного поля разрешается «последний выигрывает» |
| `place` одним значением | родитель и ключ порядка меняются одной записью | иначе два одновременных переноса дадут родителя от одного и позицию от другого |
| Ключ порядка `k` | строка между ключами соседей (дробная индексация) со случайным хвостом | два клиента, вставляющие в одно место, не получают одинаковый ключ |
| `props` | отдельный ключ на свойство | «отметил пункт» и «сменил выравнивание» одновременно не затирают друг друга |
| `text` | `Y.Text`, инлайн-атрибуты Inkbrick это атрибуты форматирования; формула и ссылка на заметку остаются одним символом U+FFFC с атрибутом (`formula`, `noteRef`) | правка формулы это смена атрибута (один победитель), а не «удалить и вставить» (две формулы) |
| `text` создаётся сразу | вместе с блоком, даже для разделителя | если создавать при смене типа, два клиента создадут два текста и один потеряется |
| Удаление | ключ блока удаляется из `blocks` вместе с потомками | правки внутри удалённого блока теряются: удаление выигрывает |
| `meta.schemaVersions` | версии схем блоков на момент создания; меняет их только миграция | клиент со старыми схемами не открывает документ новее себя |

Метаданные блока `meta` (`createdAt`, `updatedBy`) в совместном режиме не пишутся: время клиента недостоверно. Кто и когда менял
заметку, сервер знает из журнала (`author_id`).

### Проекция: из CRDT в снимок Inkbrick

Слияние может дать состояние, которого не допустил бы ни один клиент в одиночку. Снимок `{rootId, blocks}` строится чистой
функцией, одинаковой у всех, поэтому все видят одно и то же:

1. Записи неверной формы (нет `flavour`, `place` не объект) пропускаются.
2. `children` каждого блока это блоки с `place.p = id`, по возрастанию `(k, blockId)`.
3. Блоки, недостижимые от корня, прикрепляются в конец первого потомка корня (контейнер заметки) вместе со своими
   поддеревьями: сироты (родитель удалён) по своему верхнему блоку, цикл (A в B и B в A после двух одновременных переносов)
   по блоку с наименьшим `blockId`. Ничего не теряется.
4. Только на клиенте, по схеме блоков: блок, которому по `validateRelation` или глубине нельзя лежать в своём родителе,
   поднимается к первому предку, где можно, и встаёт сразу после ветки, из которой вышел; `props`, не прошедшие проверку
   схемы, заменяются значениями по умолчанию.

Правила 1–3 не зависят от схемы блоков и реализуются дважды: в мосте и на сервере. Правило 4 знает только редактор, поэтому
снимок с сервера «структурно верен», а клиент перед `deserializeDocument` прогоняет его через ту же функцию нормализации.

Проекция **ничего не пишет** в CRDT: если бы каждый клиент чинил цикл записью, клиенты перебивали бы друг друга, а починка
попадала бы в чужую историю отмены. Цикл исчезает, когда кто-нибудь снова перенесёт блок.

## Протокол

### Подключение

Как у событий задач: одноразовый билет, затем сокет.

```
POST /api/v1/notes/{note_id}/collab/ticket      Authorization: Bearer …
→ { "ticket": "…", "expires_in": 30, "write": true, "protocol": 1, "crdt_format": 1 }

GET  /api/v1/notes/{note_id}/collab?ticket=…&protocol=1
```

- Билет требует `note.read`; признак `write` ставится, если есть `note.update`. Хранилище билетов то же (`realtime.TicketStore`),
  тема `note:<id>`, в `Grant` добавляется `Write`.
- Сервер перепроверяет права по таймеру (`RecheckInterval`) и при смене роли или удалении из пространства (`Hub.DisconnectUser`).
  Потерял `note.update`, но сохранил `note.read`: соединение остаётся и становится читающим.
- Несовместимая версия протокола или формата: рукопожатие отвечает `426` с кодом `COLLAB_VERSION_UNSUPPORTED`, клиент просит
  обновить приложение.
- Проверка `Origin`, лимит соединений на пользователя, коды закрытия и пинг те же, что в [`realtime.md`](realtime.md).

### Сообщения

Кадры бинарные. Первый varuint это тип, как в `y-protocols`, поэтому кодирование на клиенте берётся из готовой библиотеки.

| Тип | Направление | Содержимое |
|---|---|---|
| `0` sync, шаг 1 | оба | вектор состояния: «что у меня есть» |
| `0` sync, шаг 2 | оба | всё, чего нет у собеседника, и полный набор удалений |
| `0` sync, update | оба | одно обновление |
| `1` awareness | оба | присутствие: курсор, выделение |
| `16` saved | сервер → клиент | `n`: первые `n` сообщений с правками этого соединения записаны в базу |
| `17` notice | сервер → клиент | JSON `{code, …}`: `READ_ONLY`, `UPDATE_REJECTED`, `RATE_LIMITED`, `NOTE_TOO_LARGE` |

- После подключения обе стороны шлют шаг 1 и отвечают шагом 2. Так же клиент досылает правки, сделанные во время обрыва:
  отдельной очереди не нужно.
- Клиент показывает «сохранено», когда `saved` догнал счётчик отправленных сообщений, и предупреждает при закрытии вкладки,
  если не догнал.
- Правки от соединения без `write` сервер отбрасывает, не разбирая, и отвечает `READ_ONLY`.
- **Периодическая сверка.** Клиент повторяет шаг 1 каждые 30 секунд, пока в заметке что-то менялось, сервер отвечает шагом 2.
  Причина найдена тестом: Yjs при получении чужих правок сам удаляет лишние метки форматирования, и набор этих удалений
  зависит от порядка доставки. Пока реплики не обменялись полным набором удалений, у одной из них фрагмент текста может быть
  оформлен иначе. Шаг 2 содержит полный набор удалений и это лечит.
- `UPDATE_REJECTED`: сервер не принял правку (превышен размер документа, обновление не разобралось). Локальный документ клиента
  теперь содержит то, чего нет на сервере, поэтому клиент обязан выбросить его и загрузить состояние заново.

### Присутствие

Состояние awareness: `{ user: { id }, selection: { anchor, focus } }`, где точки выделения это относительные позиции Yjs
(`blockId` плюс позиция в `Y.Text`), а не смещения. Сервер:

- привязывает `clientID` к соединению при первом сообщении и не пропускает записи с чужим `clientID`;
- подставляет `user.id` из билета, что бы ни прислал клиент; имя, аватар и цвет клиент берёт по `id` из обычного API;
- при закрытии соединения рассылает удаление его записей;
- ничего не хранит.

## Сервер

### Пакеты

| Пакет | Назначение |
|---|---|
| `internal/collab/ydoc` | единственное место, где импортируется `ygo`: применить обновление, вектор состояния, разница, слияние, проекция в снимок, начальный документ |
| `internal/collab` | комнаты: соединения, протокол, права на запись, лимиты, пакетная запись, awareness |
| `internal/service` (`note_content_service.go`) | сборщик производных данных: снимок, текст, ссылки, версии |
| `internal/repository` | `note_crdt_repository.go`: журнал и состояние |
| `internal/handler` | билет и рукопожатие рядом с `realtime_handler.go` |

Существующий `realtime.Hub` не меняется: он рассылает JSON-события в одну сторону. Комнаты отдельно, потому что читают
бинарные кадры от клиента и держат состояние.

### Комната

Одна на открытую заметку в процессе.

1. **Открытие** (первое соединение): прочитать `note_crdt_state` и хвост `note_crdt_updates`, собрать `ygo`-документ.
2. **Правка от клиента**: лимит размера и частоты → применить к документу комнаты (`ApplyUpdateV1Landed` возвращает только то,
   чего в документе ещё не было) → пусто, значит повтор, дальше не идёт → разослать остальным соединениям → положить в пачку
   на запись.
3. **Запись** раз в 200 мс или по 64 КиБ: обновления одного автора за это время сливаются (`MergeUpdatesV1`), одна транзакция
   пишет строки журнала и отметку «заметка изменена». После коммита клиентам уходит `saved`.
4. **Закрытие** через минуту после последнего соединения: запись остатка, сжатие, выгрузка из памяти.

Рассылка идёт раньше записи: задержка для соавторов минимальна. Если процесс упадёт между рассылкой и записью, правка не
пропадёт, пока жив хоть один клиент: при переподключении шаг 2 дошлёт всё, чего нет на сервере. Автор при этом не увидит
«сохранено».

Сбой записи: повторы с растущей задержкой, правки остаются в памяти комнаты; после нескольких неудач комната закрывает
соединения кодом 1011, клиенты переподключаются и досылают.

### Хранение

```sql
note_crdt_state   (note_id PK, state BYTEA, last_seq BIGINT, compacted_seq BIGINT,
                   dirty_since TIMESTAMPTZ NULL, updated_at)
note_crdt_updates (note_id, seq BIGINT, update BYTEA, author_id, created_at, PRIMARY KEY (note_id, seq))
```

- `seq` считается на заметку: транзакция записи блокирует строку `note_crdt_state` (`FOR UPDATE`), увеличивает `last_seq` и
  вставляет строки. Общий `BIGSERIAL` не годится: номера выдаются не в порядке коммита, и читатель хвоста пропустил бы строку.
- Состояние заметки это `state` плюс все обновления с `seq > compacted_seq`.
- **Сжатие**: когда хвост длиннее 500 строк или 1 МиБ и при закрытии комнаты. Под той же блокировкой: `state` = закодированный
  документ комнаты, `compacted_seq = last_seq`, строки журнала до него удаляются. Документ комнаты работает со сборкой мусора,
  поэтому содержимое удалённого текста в `state` не хранится.
- Новая заметка: сервер создаёт начальный документ сам (`meta`, корень, контейнер, пустой абзац) в транзакции создания. Если бы
  это делал клиент, два одновременно открывших пустую заметку создали бы структуру дважды. Заметка из шаблона или импорта:
  клиент строит начальное обновление мостом и передаёт его в `POST …/notes` (`seed`), сервер применяет его к пустому документу,
  проверяет проекцией и лимитами.

### Производные данные

Отметка `dirty_since` ставится при записи пачки. Сборщик (фоновый цикл по образцу воркера outbox: `FOR UPDATE SKIP LOCKED`,
аренда) берёт заметки, в которых три секунды тихо или которые «грязные» дольше тридцати секунд, и в одной транзакции:

1. собирает документ из `state` и хвоста, строит снимок (проекция, правила 1–3);
2. пишет `notes.content` (JSON), `content_text` (плоский текст для `pg_trgm`), `snapshot_seq`;
3. пересобирает `note_links` из атрибутов `noteRef` и внутренних ссылок `/n/<id>` в тексте; данным клиента о связях не верит;
4. при необходимости пишет версию (ниже) и запись активности `note.updated`: одну на автора за интервал, а не на каждую правку;
5. снимает `dirty_since`, если `last_seq` не вырос.

После коммита уходит событие `note.updated` для списков и боковых панелей. Обратные ссылки и поиск отстают от правок на
несколько секунд, это допустимо.

`GET /notes/{id}` отдаёт `content` и `snapshot_seq`. Читателю без открытого редактора этого достаточно; редактор всегда
подключается к комнате и берёт состояние оттуда.

### Версии и откат

- `note_versions(id, note_id, seq, title, content JSONB, created_by, created_at, label NULL, kind)`; `kind`: `auto`, `manual`,
  `restore`.
- Автоматическая версия: сборщик пишет её, если с прошлой прошло больше десяти минут и содержимое изменилось, и когда комната
  закрылась после правок. Ручная: `POST /notes/{id}/versions` с меткой.
- **Откат делает редактор, а не сервер.** `POST /notes/{id}/versions/{n}/restore` проверяет `note.update`, записывает версию
  «до отката» и возвращает снимок; мост применяет его как обычную локальную правку (блоки с тем же `id` правятся на месте,
  лишние удаляются, недостающие создаются). Соавторы видят откат как правку, автор может отменить его через undo, а серверу не
  нужен второй экземпляр логики моста на Go.
- Хранить версии как JSON, а не как снимки Yjs: документ со сборкой мусора старое состояние восстановить не может.

### Лимиты (стартовые значения, уточнить под нагрузкой)

| Что | Значение | При превышении |
|---|---|---|
| Кадр | 1 МиБ, как тело REST | закрытие 1009 |
| Соединений на пользователя | общий счётчик с событиями, 10 | 429 при рукопожатии |
| Соединений на заметку | 50 | 429 |
| Правок с соединения | 60 кадров в секунду, 4 МиБ в минуту | `RATE_LIMITED`, затем закрытие 1008 |
| Обновления с неизвестными зависимостями | 1 МиБ в ожидании на комнату | `UPDATE_REJECTED` |
| Размер состояния | 8 МиБ | `NOTE_TOO_LARGE`, правка не принимается |
| Awareness | 4 КиБ на запись, 10 в секунду | запись отбрасывается |

Картинки в документ не встраиваются (`images.upload` обязателен), иначе лимиты съедят `data:`-адреса.

Отказ от уже применённой правки: документ комнаты пересобирается из базы без неё, отправитель получает `UPDATE_REJECTED`.

### Безопасность

| Угроза | Защита |
|---|---|
| Читатель шлёт правки | отбрасываются по типу сообщения до разбора |
| Редактор шлёт мусор | обновление, которое не разбирается, не применяется и не рассылается; повторные попытки закрывают соединение |
| Редактор портит документ корректными правками | это его право; защита версиями и журналом с `author_id` |
| Чужое имя у курсора | `user.id` подставляет сервер, `clientID` привязан к соединению |
| Билет утёк в журнал | параметр `ticket` уже вырезается перед записью журнала доступа; билет одноразовый и живёт 30 секунд |
| Доступ отозван при открытом сокете | перепроверка по таймеру и `DisconnectUser` |
| Раздувание документа или памяти | лимиты выше; комната выгружается после закрытия |
| Вредная ссылка в атрибуте | редактор показывает ссылку только после `isSafeUrl`; сервер в `note_links` берёт только идентификаторы заметок нужного формата и только из своего пространства |

### Несколько реплик (позже)

Обновления CRDT можно применять в любом порядке и повторно, поэтому комнату одной заметки могут держать несколько процессов
сразу: владелец не нужен. Что добавить:

- после записи пачки `NOTIFY note_crdt, '<note_id>:<seq>'`; процесс, у которого открыта эта комната, читает строки журнала после
  своего последнего `seq`, применяет и рассылает своим соединениям;
- awareness через тот же `NOTIFY` (записи маленькие);
- сжатие и сборщик уже защищены блокировкой строки;
- билеты: общее хранилище или липкая маршрутизация, как и для событий задач.

### Наблюдаемость

Метрики: открытые комнаты и соединения, принятые и отброшенные правки (по причине), задержка записи пачки, длина хвоста журнала,
размер состояния, отставание сборщика (`now − dirty_since`), длительность сборки снимка. В `alerts.yml`: рост хвоста без сжатия,
отставание сборщика больше пяти минут, доля отброшенных правок.

## Клиент

- Транспорт пишется свой, поверх `y-protocols`: готовый `y-websocket` не умеет брать новый билет на каждое подключение и не
  знает сообщений `saved` и `notice`. Это около двухсот строк в приложении; пакет `@inkbrick/collab` о сети не знает.
- Входящие обновления транспорт передаёт мосту (`collab.receive`), а не применяет к `Y.Doc` сам: мост придерживает их, пока идёт
  ввод через IME.
- Переподключение с растущей задержкой и новым билетом. Правки, сделанные без связи, лежат в `Y.Doc` в памяти и уходят шагом 2.
- Офлайн позже: тот же `Y.Doc` дополнительно пишется в IndexedDB; протокол не меняется. Отдельно решить, что делать с правками
  человека, у которого отобрали права, пока его не было (сервер их отбросит: сохранить копией).

## Что проверено и что нет

Проверено тестом [`tests/crdt-compat`](../tests/crdt-compat/README.md): `yjs` 13.6.33 против `reearth/ygo` 1.55.0 на формате
документа выше. Три реплики Yjs делают случайные правки (текст с кириллицей и эмодзи, атрибуты, свойства, перенос, смена
типа, удаление блоков), Go получает их обновления.

- Go читает состояние Yjs, Yjs читает состояние Go (V1 и V2), слияние обновлений без документа и векторы состояния совпадают,
  правки, сделанные в Go, применяются в Yjs, и Yjs продолжает работать поверх них.
  Прогон `./run.sh 40`: 80 сценариев (40 по 3000 правок по порядку, 40 по 600 в случайном порядке), все проверки прошли.
- При одном и том же порядке доставки Go и Yjs дают одинаковый результат. Расхождение с эталоном встретилось в одном
  сценарии из 80 (в черновых прогонах чаще, до нескольких на сотню) и каждый раз было свойством самого Yjs: оформление одного
  блока зависело от порядка доставки и выравнивалось после обмена полным состоянием (см. «Периодическая сверка»).
- Состояние, закодированное Go в V1, на 27–74 % больше, чем у Yjs; в V2 от −8 до +21 % к размеру Yjs V1. Хранить `state`
  стоит в V2, по сети оставить V1.
- Особенности `ygo`, на которые наткнулся тест: `YMap.ForEach` пропускает вложенные типы (обходить через `Keys` и `Get`);
  чтение внутри `Transact` блокируется навсегда (типы получать до транзакции).
- Для моста: Yjs заменяет половинки разорванной суррогатной пары на U+FFFD только у той реплики, которая её разорвала, и
  реплики показывают разный текст. Смещения вставки и удаления не должны попадать внутрь пары.

Не проверено:

- мост Inkbrick ↔ Yjs целиком (его проверяет прототип, этап K0), в том числе отмена удаления блока через менеджер отмены Yjs;
- сборка мусора и ожидающие обновления в `ygo` под нагрузкой, awareness из `ygo`, поведение на документах в мегабайты;
- производительность комнаты и сборщика: цифр нет, лимиты выше это стартовые значения;
- работа за nginx и TLS (то же, что уже числится за WebSocket в [`backlog.md`](backlog.md)).

Зависимость от `ygo`: версия закрепляется, тест совместимости становится обязательным в CI в тот же PR, где `ygo` появляется в
`go.mod`, и запускается при обновлении `ygo` или `yjs`. Пакеты `crdt`, `sync`, `awareness` тянут только стандартную библиотеку.

## Этапы

| Этап | Где | Что | Готово, когда |
|---|---|---|---|
| K0 | Inkbrick | прототип моста `@inkbrick/collab` без сервера: два редактора на странице песочницы | фазз-тест сходимости зелёный, перенос блоков, undo и IME не ломаются |
| K1 | сервер | таблицы заметок и CRDT, права `note.*`, метаданные по REST, начальный документ, билет, комната, запись, `saved` | два клиента Yjs из теста редактируют через сервер, перезапуск сервера ничего не теряет |
| K2 | сервер | сборщик: снимок, поиск, `note_links`, обратные ссылки; сжатие; метрики и алерты | снимок и ссылки совпадают с тем, что видит редактор |
| K3 | приложение, Inkbrick | транспорт, подключение редактора, присутствие и курсоры | два человека редактируют одну заметку в приложении |
| K4 | Inkbrick, сервер | ссылки `[[…]]` (варианты A и B из `notes-design.md`), пакетное получение названий | ссылка переживает копирование, экспорт и совместную правку |
| K5 | сервер, Inkbrick | версии, откат через редактор, политика хранения | откат виден соавторам как правка |
| K6 | сервер, приложение | несколько реплик, офлайн | по триггеру: рост нагрузки, запрос на офлайн |

K0 и K1 идут параллельно: их связывает только формат документа и общие тестовые данные. K0 самый рискованный, по нему
возможна правка формата (например, если отмена удаления блока окажется ненадёжной, удаление станет отметкой, а не удалением
ключа), поэтому до его завершения формат не замораживается.
